# Дополнительные источники данных — что мы проверили

Мы оценивали **Bloomberg** для новостей и **Polymarket**, **Kalshi**,
**ForecastEx** для вероятностей событий. Расширенный анализ Polymarket теперь
разделяет US и международный сервис. **Polymarket US технически подходит для
интеграции только для чтения; локальный MVP реализован и проверен. Права компании
и закрытый доступ сотрудников в рабочем сервисе ещё нужно обеспечить.**
ForecastEx остаётся другим вариантом для оценки.
Разделы об остальных поставщиках сохраняют результаты прежней проверки.

## Bloomberg — нет

У Bloomberg лучшие данные. **Проблема в их договоре, а не в цене.**

Их лицензия, которую мы прочитали сами, запрещает хранить данные в базе,
передавать их кому-либо, использовать в автоматизированной системе и
подключаться с машины, не залогиненной в Терминал. Наш сервис делает всё
четыре. Место стоит **$31 980 в год**, и покупка не помогает — ограничения идут
вместе с ним.

Есть фиды, для которых Терминал не нужен, но они рассчитаны на торговые
подразделения, а не на показ читателям. Единственный продукт, где публикация
*разрешена*, — отдельный медиа-бизнес, и продаётся он по темам («Технологии»,
«Энергетика»), а не по компаниям. То есть даже за деньги он не отвечает на
вопрос «новости по этой компании».

Это не изменится: их лицензия закрывает всё, что может заменить подписку на
Терминал.

## Polymarket — интеграция US технически возможна; права компании пока не подтверждены

**Обновлено 9 сентября 2026 года; сохранённые ответы API получены 8 сентября.**
Планируемый рабочий сценарий — аналитический
блок для сотрудников рядом с новостями, без торговли. **Polymarket US и
международный Polymarket — разные продукты:** их API, аккаунты, рынки и условия
нужно оценивать отдельно. Аккаунт US не даёт доступ к международному каталогу
Gamma/CLOB. Публичные US API и локальная версия проверены. Закрытые учётные данные
аккаунта и реальный авторизованный поток поставщика не изучались и не проверялись.

### 1. Что проверено на Polymarket US

Прямые запросы с этой машины прошли **без VPN, входа в аккаунт и API-ключа**.
Прежний вывод о сетевой недоступности к US-сервису неприменим. Доступность с
будущего сервера развёртывания нужно проверить отдельно.

| Проверка чтения данных | Результат 8 сентября |
| --- | --- |
| `GET /v1/markets?limit=3&active=true&closed=false` | HTTP 200; три действующих спортивных контракта с описаниями и котировками |
| `GET /v1/markets/{slug}/bbo` и `/book` | HTTP 200; цены покупки/продажи, количества заявок и рыночная статистика |
| `GET /v1/search?query=Fed&limit=3` | Решения ФРС в сентябре и октябре, а также событие о повышении ставки в 2026 году; статус active/open |
| Поиск событий о процентных ставках | Решения центробанков Бразилии, Мексики и Японии; по мексиканскому контракту также получен непустой стакан |
| `GET /v1/price-history` для одного спортивного контракта | HTTP 200; за час данных не было, за сутки получена одна точка |

Базовый адрес — `https://gateway.polymarket.us`. Это небольшие проверки
доступности и формата, **а не исследование ликвидности или надёжности в рабочем
режиме**. Вводная страница ещё описывала финансовые рынки как будущую функцию,
но действующий API уже возвращал макрособытия. Поиск инфляции, напротив, не дал
результатов; одного такого запроса недостаточно, чтобы утверждать, что этих
рынков нет во всём каталоге.
[Публичный API](https://docs.polymarket.us/api-reference/introduction),
[список рынков](https://docs.polymarket.us/api-reference/markets/get-markets),
[поиск](https://docs.polymarket.us/api-reference/search/search).

Поздняя сохранённая выборка ФРС включала пять контрактов, изображение события,
249 суточных и 57 недельных исторических точек с пропусками. Отдельный перечень
содержит точное время запросов, поля ответов и снимки; эти наблюдения нельзя
подменять актуальными котировками.

### 2. Варианты подключения и частота обновлений

| Канал | Данные и доступ | Применение у нас |
| --- | --- | --- |
| Публичный REST: `gateway.polymarket.us` | Рынки/события, поиск, изображения, котировки, стаканы, расчётные цены и история; ключ не нужен | Канал локального MVP; до регулярного рабочего использования подтвердить права компании |
| Розничный WebSocket: `wss://api.polymarket.us/v1/ws/markets` | Авторизация API-ключом; обновления стаканов, цен и сделок в реальном времени | Необязательное подключение реализовано; ключи и поток поставщика не проверены |
| Прямой доступ к данным биржи | REST/gRPC только для чтения: справочники, BBO, глубина и статистика; выдаваемые учётные данные | Прямо описанный вариант для исследовательских команд и аналитических платформ |

Для публичного API указан лимит **20 запросов в секунду на IP**. REST возвращает
снимок на момент запроса: **опрос раз в 10 секунд** в локальном MVP не сохраняет
каждое промежуточное изменение. У истории отдельные интервалы кэширования и
выборки. Розничный WebSocket допускает до 100 рынков на подписку и объединение
обновлений в пакеты. Успешный запрос и обозначение «реальное время» не дают
гарантии задержки. Авторизованный поток мы не измеряли.
[Публичные лимиты](https://docs.polymarket.us/api-reference/rate-limits),
[WebSocket](https://docs.polymarket.us/api-reference/websocket/markets),
[руководство по данным](https://docs.polymarket.us/data-guide/overview).

Для розничного ключа документация требует регистрации в приложении и проверки
личности, затем генерации ключа в кабинете разработчика; розничный API описан
как вариант для личных аккаунтов. К анонимному публичному REST это требование
не относится. Институциональный поток данных использует другие учётные данные
и права доступа; его документация прямо говорит, что торговый KYC и ID участника
не нужны, но договорное подключение остаётся. Личный вход в аккаунт, таким
образом, не нужен для публичного чтения и не подтверждает права компании.
[Розничная авторизация](https://docs.polymarket.us/api-reference/authentication),
[типы API](https://docs.polymarket.us/trader-guide/api-overview),
[институциональный поток](https://docs.polymarket.us/streaming-endpoints/market-data-stream).

У институционального API другие лимиты: для стакана/BBO указано 12 запросов в
минуту на компанию; для частых обновлений предусмотрен поток. **Нельзя переносить
частоту опроса публичного REST на институциональное подключение.**
[Лимиты биржевого API](https://docs.polymarket.us/trader-guide/rate-limits).

### 3. Что разрешено и что пока не подтверждено

Публичная документация прямо предлагает создавать приложения с рыночной
информацией. Однако условия US включают API и дают лицензию на личное
некоммерческое использование данных для собственной торговли (§5); автоматизация
через разрешённые API допускается (§7). **Наш вывод: права на аналитику компании
этим не подтверждаются.** Доступный адрес и лицензия на код SDK вопрос не решают.
[Условия US от 25 сентября 2025 года](https://polymarket.us/tos).

Таблица ниже определяет нужный нам объём прав, а не утверждает, что каждый пункт
обязательно требует отдельного платного продукта:

| Планируемое действие | Положение для нашего проекта |
| --- | --- |
| Читать документированные публичные API без ключа | Технически предусмотрено; небольшие проверочные запросы прошли |
| Регулярно собирать данные и показывать сотрудникам | Подтвердить применимость публичного канала к нашей компании либо согласовать другой |
| Хранить снимки, исходные ответы, резервные копии и графики | Уточнить сроки, историческое использование и удаление; права проекта пока не установлены |
| Показывать изображения событий или копировать статьи | Подтвердить права на контент/изображения; URL и публичная статья не дают безусловной лицензии |

У Polymarket US есть процедура получения **Market Data Agreement** через

### 4. Локальный MVP и рабочая архитектура

**Реализованная локальная версия:** страница Next.js **`/polymarket`** → серверный
адаптер → публичный REST Polymarket US. Она объединяет поиск/темы, изображения,
цены YES/NO, график по времени с выделенными пропусками, стакан, статистику,
правила и карточки статей из отдельных источников. Котировки/стакан обновляются
каждые **10 секунд**; история кэшируется 30 секунд, данные события обновляются
раз в 60 секунд, новости — раз в пять минут. Скрытая вкладка и ручная пауза
останавливают опрос. Панель AI скрыта, цены не передаются в её AI-конвейер.
Необязательный серверный WebSocket передаёт статус, котировки и стакан через
SSE; локальных ключей нет, реальный авторизованный поток не проверен.
**9 сентября в 02:27:04 UTC** завершены 11 браузерных проверок: реальные данные,
обновление, пауза, выбор контракта, работа с графиком, подпись ошибок/старых данных,
мобильный экран и тёмная тема. Прошли 19 модульных тестов, TypeScript,
ESLint изменённого кода и production build. Реальные снимки, отдельная выборка
графика с **243 точками и четырьмя пропусками** и точное время приведены в
[перечне данных](../polymarket/data-inventory.ru.md).

**Новости поступают отдельно.** Описания в API Polymarket — правила контрактов,
а не тексты статей. Polymarket публикует журналистику в **The Oracle**, а
международные Journalism Tools показывают новости рядом с графиками рынков.
Но поддерживаемый endpoint новостей/статей в индексе US API не найден. Для блока
**«Связанные новости»** MVP использует существующие источники платформы, сохраняя
издателя и ссылки. Близость темы не доказывает, что статья вызвала движение цены.
Изображения событий доступны в US API; права на них нужно включить в рабочий
объём использования.
[The Oracle](https://news.polymarket.com/about),
[Journalism Tools](https://news.polymarket.com/p/new-polymarket-tools-for-journalists),
[индекс US API](https://docs.polymarket.us/llms.txt).

Проверенный запрос новостей вернул девять результатов с восемью URL изображений;
видны шесть карточек. Самая новая статья датирована **30 августа 2026 года**:
доступность провайдера не означает получение новостей в реальном времени.

**Будущая рабочая схема:** Polymarket US API → единый серверный сборщик → отдельные таблицы
прогнозных рынков в Postgres → внутренний API с авторизацией → блок для
сотрудников рядом с макроновостями. Локальная версия не реализует этот постоянный
сбор и рабочее развёртывание для сотрудников.

В отдельном `news-service` уже есть TypeScript, Fastify, Postgres, задачи сбора и
необязательный планировщик, по умолчанию выключенный. Интерфейс новостного
поставщика возвращает статьи с привязкой к
листингам компаний; контрактам событий нужен отдельный модуль, а не запись в
`NEWS_PROVIDER_ORDER`. Приложение Next.js уже обращается к этому сервису по HTTP
через `src/features/global-news/lib/newsService.ts`.

| Рабочий компонент | Предлагаемое изменение после локальной версии |
| --- | --- |
| Сборщик | Отдельная задача с блокировкой повторного запуска; сначала 20 выбранных макроконтрактов, метаданные раз в 15 минут, BBO раз в 30–60 секунд |
| Хранение | Определения рынков, идентификаторы исходов, снимки и статус сбора; сохранять продукт-источник, ID, slug, правила и время источника/получения |
| Внутренний API | Список, карточка, история и статус рынков; отдавать сохранённые данные, чтобы каждый просмотр страницы не обращался к Polymarket |
| Интерфейс | Необязательный блок «Рынки событий» в `GlobalNewsPage`: ссылка, точный вопрос/исход, тип цены, давность, статус и спред |
| Эксплуатация | Ошибки, ответы 429, отсутствующие/устаревшие котировки, последний успешный сбор; отказ блока не должен ломать новости |

Для этого отдельного рабочего варианта двадцать запросов по контрактам каждые
30 секунд — в среднем **0,67 запроса в
секунду**, без учёта метаданных, истории и стаканов. Это расчёт нагрузки для
предлагаемого пилота, а не разрешение или гарантия актуальности. Запросы нужно
распределять во времени; общий лимит учитывает все процессы сбора, использующие
один внешний IP. Полные стаканы сначала получать выборочно по необходимости. Сам показ
рыночного контекста рядом с новостями не требует потокового подключения.

**Что нужно до рабочего развёртывания для сотрудников:**

- **Обеспечить доступ только сотрудников.** Корневое приложение описано как
  однопользовательское, без авторизации. Токен бэкенда сейчас защищает запуск
  сбора, а не чтение. Нужна авторизация сотрудников для блока и API, а также
  ограниченный доступ к сервису. CORS и скрытая ссылка этого не обеспечивают.
- **Ограничивать запросы именно по секундам.** Существующий поминутный лимитер
  стартует с полным запасом; настройка 1 200/мин допускает всплеск, несовместимый
  с ограничением 20/с.
- **Сохранять точность чисел.** Бэкенд глобально преобразует Postgres `NUMERIC`
  в числа JavaScript. Для цен нужны проверенные десятичные строки или целые
  ценовые шаги; единицы количества и оборота необходимо уточнить до расчётов.
- **Хранить ключи подписи на сервере.** Существующую схему браузерного потока
  котировок акций нельзя копировать для секретного ключа Polymarket. Поток должен
  обслуживать управляемый серверный процесс с переподключением и восстановлением
  состояния по снимкам.
- **Исключить данные из AI-запросов первого этапа.** Исследовательский конвейер
  передаёт входные данные Anthropic. Подключать к нему новый источник отдельно,
  после подтверждения обработки и использования производных результатов.

Проверенные файлы: бэкенд — `src/features/global-news/providers/types.ts`, `src/features/global-news/ingest/scheduler.ts`,
`src/util/rateLimiter.ts`, `src/db/pool.ts`, `src/api/server.ts`,
`src/features/global-news/api/routes/operations.ts`; фронтенд — `README.md`, `src/features/global-news/lib/newsService.ts`,
`src/features/global-news/components/GlobalNewsPage.tsx`, `src/features/companies/lib/useLiveQuote.ts`,

### 5. Интерпретация данных и проверки перед запуском

**Цена контракта отражает рыночную оценку, а не проверенную вероятность события.**
Цены покупки, продажи, последней сделки и отображаемая цена должны различаться.
Показывать спред, отсутствие одной стороны, давность сделки и статус; не заменять
отсутствующие данные нулём. Контракт ФРС — макроконтекст, а не автоматически
новость о каждой компании. Объединять исходы можно только после проверки, что
по правилам расчёта они взаимоисключающие и исчерпывающие.

Исторический API возвращает **цены YES/NO, полученные из стакана**, а не историю
исполненных сделок. YES обычно соответствует лучшей цене продажи, NO — единице
минус лучшая цена покупки; из-за спреда сумма может превышать единицу. Разные
временные окна используют разную частоту выборки; одинаковые запросы истории
нужно кэшировать минимум на 30 секунд. Историю поставщика и собственные снимки
следует подписывать отдельно. Первоначальная спортивная выборка была пустой/редкой;
поздняя выборка ФРС содержала 249 суточных и 57 недельных точек с пропусками.
Ни одна не подтверждает полноту истории для каждого контракта.
[История цен](https://docs.polymarket.us/api-reference/price-history/get-price-history).

В одном реальном ответе порядок устаревших массивов `outcomes`/`outcomePrices`
не согласовывался с явными `marketSides`. Нужно проверять ID стороны, `long`,
описание и поля котировки; **нельзя просто объединять старые массивы по индексу**.
Официальный TypeScript SDK поддерживает публичное чтение, но в проверенных типах
рынка нет `marketSides`, а в модуле рынков — метода истории. Для начала лучше
небольшой REST-адаптер с проверкой ответов; при использовании SDK зафиксировать
версию и не полагаться только на его типы.
[Схема рынка](https://docs.polymarket.us/api-reference/markets/get-markets),
[типы SDK](https://github.com/Polymarket/polymarket-us-typescript/blob/main/src/types/markets.ts),
[модуль рынков SDK](https://github.com/Polymarket/polymarket-us-typescript/blob/main/src/resources/markets.ts).

Закрытие рынка и окончательный расчёт — разные состояния. Отсутствие ответа с
расчётной ценой может означать, что расчёт ещё не выполнен; некоторые контракты
допускают альтернативные значения. Нужно сохранять точные правила и статус, а
не считать, что любой закрытый рынок уже рассчитан в ноль или единицу.
[Расчётная цена](https://docs.polymarket.us/api-reference/markets/get-market-settlement),
[правила расчёта](https://docs.polymarket.us/learn/markets/contract-settlement).

В выборке мексиканский контракт имел цену покупки 0,98 и продажи 0,99, причём на
лучшей покупке было лишь 19,17 единицы; последняя сделка состоялась в предыдущий
день. Это одно наблюдение, а не вывод о всей ликвидности. В согласованном пилоте
нужно измерить спред, глубину, давность сделок, пропуски и доступную историю по
каждому выбранному контракту, прежде чем считать поток полезным сигналом.

Проверки должны охватывать сопоставление исходов, единицы и точность чисел,
редкую историю, закрытие/расчёт, повторные запросы и 429, дубли сбора, отметки
устаревания, запрет чтения без авторизации и исключение данных из AI/выгрузок.
Перед включением необязательного потока проверить реальный формат сообщений и восстановление после
разрыва: примеры в обзорной и подробной документации сейчас различаются.
Полное восстановление пропущенных обновлений нельзя обещать без проверки.
[Обзор WebSocket](https://docs.polymarket.us/api-reference/websocket/overview),
[подробное описание потока](https://docs.polymarket.us/api-reference/websocket/markets).

### 6. Что можно сделать сейчас и какие решения нужны

1. **Использовать проверенную локальную версию:** выбор событий, цены,
   изображения, графики, REST раз в 10 секунд и отдельные источники новостей
   проверены; реальные снимки и обработка отказа зафиксированы. Синтетические
   примеры полезны для особых случаев; рабочий MVP не подтверждает права на
   промышленное использование. Постоянный фоновый сбор пока оставить выключенным.
2. **Уточнить конкретное использование:** спросить, разрешён ли нашей компании
   публичный gateway для регулярной внутренней аналитики либо нужен Market Data
   Agreement. Указать юрлицо и страну, расположение сотрудников/серверов,
   аудиторию, поля, сроки хранения, резервные копии, изображения, производные показатели и
   внешних обработчиков. Запросить разрешённый канал, цену/условия пилота и
   удаление данных. Письмо не отправлялось, договор и платный доступ не принимались.
3. **Провести согласованный REST-пилот:** предлагаем одну неделю, 20 нужных
   контрактов, закрытый доступ сотрудников и измерение качества. Проверить сеть
   с будущего сервера. Срок и размер списка — проектные предложения, а не
   предоставленные поставщиком права.
4. **Принять решение о рабочем запуске:** нужны подтверждённый объём прав и
   полезное покрытие/актуальность. Поток добавлять по результатам измерений;
   AI рассматривать как отдельное расширение. Цена лицензии неизвестна;
   публичный доступ не доказывает бесплатное коммерческое использование.

### 7. Международный Polymarket — отдельный вариант

Для `polymarket.com` проверенные прямые соединения сбрасывались; внешний сервис
чтения вернул запись Gamma и время CLOB. Это подтверждает ограниченное получение
данных, а не надёжный рабочий канал. Интерфейсы Gamma, CLOB и WebSocket нельзя
смешивать с US API и учётными данными US.
[Международные API](https://docs.polymarket.com/market-data/discover-markets).

Полные встроенные условия удалось получить автоматически. Редакция от
11 августа 2026 года, §4.2, ограничивает доступ/использование для указанных
участников рынков капитала, включая определённые финтех-компании и поставщиков
данных, и отдельно — распространение. Охвачены производные/агрегированные данные;
явного исключения для внутреннего пилота нет. Применимость зависит от деятельности
нашего юрлица. §4.1 ограничивает обход через VPN; другой сетевой маршрут права
не меняет.
[Международные условия](https://docs.google.com/document/d/1N4aYlRcqaWCeKMID7vUSWJ1UPMvw_v6SP4cOFN8ZxR4/preview).

ICE объявила об эксклюзивной дистрибуции для институциональных рынков капитала;
международный Polymarket направляет соответствующие компании к своей команде
лицензирования и ICE. Контакт — **data-licensing@polymarket.com**. Нужно уточнить
права, канал и цену; это не обязательно покупка ключа API. **Вывод об ICE нельзя
переносить на Polymarket US:** документация US предусматривает собственное прямое
подключение к данным. Цена обоих вариантов для нашего проекта не установлена.
[Объявление ICE](https://ir.theice.com/press/news-details/2026/ICE-Launches-Polymarket-Signals-and-Sentiment-Tool-Turning-Crowd-Sourced-Dynamic-Views-into-Market-Opportunities/default.aspx),
[международное лицензирование](https://institutional.polymarket.com/).

## Kalshi — нет

Полноценно регулируемая американская биржа, выглядела перспективно. Но их
developer agreement, который мы прочитали сами, ограничивает API
*«обслуживанием собственной торговли участника»* и запрещает *«сбор,
кэширование, агрегацию и хранение данных»*.

Проще говоря: **их API — чтобы торговать, а не чтобы строить на нём продукт.**
Показ их цен пользователям — ровно то, что запрещено. Плюс тоже заблокирован на
сети.

## ForecastEx — стоит попробовать

**Этот вариант работает.** ForecastEx — американская биржа под регулированием
CFTC, и это регулирование **обязывает её публиковать дневные цены.** Она их и
публикует — обычными CSV-файлами на сайте.

Мы их скачали: без ключа, без аккаунта, данные актуальные. По каждому рынку за
день — цена открытия, максимум, минимум, закрытие, цена расчёта и открытый
интерес, то есть полная история движения вероятностей. Покрытие: инфляция (CPI),
решения ФРС по ставке, занятость, заявки на пособия, ВВП, розничные продажи,
строительство жилья, выборы.

**Права всё равно нужно проверить:** прежний анализ отнёс эти файлы к обязательному
регуляторному раскрытию и не выявил применимых условий повторного использования.
Обязанность публиковать данные сама по себе не разрешает нашу интеграцию.

**Проверить в первую очередь:** основной объём торгов там — в *погодных* рынках.
Экономические рынки существуют, но хватает ли в них денег, чтобы цифрам можно
было верить, мы не измеряли.

## Предложение

Оценивать **Polymarket US вместе с ForecastEx** для блока рыночного контекста
сотрудников. Проверенный US API и действующие макрорынки меняют прежние основания
для приоритета только ForecastEx. Сохранить новостной конвейер и выделить данные
прогнозных рынков в отдельный модуль.

Использовать проверенную локальную US-версию, параллельно подтверждая конкретный объём прав
компании. Затем провести небольшой согласованный REST-пилот для сотрудников
и измерить качество. Для ForecastEx также нужно проверить права и
ликвидность: сама публикация данных не даёт безусловной лицензии на повторное
использование. Международному Polymarket нужна отдельная оценка подключения и
лицензирования. Локальный MVP не является рабочим развёртыванием; обращение
за лицензией не выполнялось.
